PART 0b - the target hour: is local standard noon really 18:00 UTC?
==========================================================================
DECISIONS D33 sets DSM's target hour to local standard noon with
daylight saving deliberately ignored, and says that is 18:00 UTC. This
checks it against the timezone database rather than taking it on trust.

timezone from IEM metadata : America/Chicago
  mid-winter (standard time)    : 18:00 UTC = 12:00 CST (UTC-6)
  mid-summer (daylight saving)  : 18:00 UTC = 13:00 CDT (UTC-5)
  standard-time offset          : UTC-6
  so local standard noon (12:00) = 18:00 UTC
  D33 says                       = 18:00 UTC
  VERDICT                        : MATCHES

For contrast, what 12:00 UTC would have been at DSM:
  mid-winter  : 12:00 UTC = 06:00 CST - dawn
  mid-summer  : 12:00 UTC = 07:00 CDT - dawn
That is the dawn transition SPEC 4.1 chose 12:00 UTC to avoid in Europe,
which is why D33 moved the hour rather than keeping it.

PART B6 - US-specific check 2: are the timestamps really UTC?
==========================================================================
Every IEM request in this project sends tz=UTC. In Europe that was easy
to take on trust. At DSM, local time is 5 or 6 hours behind UTC, so a
mistake here would be large and silent. The same three days were pulled
a second time with tz=America/Chicago, so the two can be compared.

UTC-request file        : iem_asos_DSM_2026-07-01_2026-07-04_routine-tmpc-tmpf.csv
local-request file      : iem_asos_DSM_2026-07-01_2026-07-04_routine-localtime.csv
rows, UTC request       : 72   first 2026-07-01 00:54:00, last 2026-07-03 23:54:00
rows, local request     : 72   first 2026-07-01 00:54:00, last 2026-07-03 23:54:00

The two files carry the same stamps (00:54, 01:54, ...) but different
values, which is what a real timezone shift looks like: the same clock
face is a different moment in each. So the test is: how far do the two
series have to be slid past each other before the temperatures line up?

  shift (hours)   rows compared   temperatures equal
             +0              72        3  (4.2%)
             +1              71        4  (5.6%)
             +2              70        4  (5.7%)
             +3              69        9  (13.0%)
             +4              68       17  (25.0%)
             +5              67       67  (100.0%)
             +6              66       17  (25.8%)
             +7              65        7  (10.8%)
             +8              64        4  (6.2%)

  best match: the UTC series is 5 hours ahead of the local
              series (100.0% of temperatures identical).
  Expected in early July: America/Chicago is on daylight saving, UTC-5,
  so a UTC stamp should sit 5 hours ahead of the same local moment.
  VERDICT: MATCHES - the tz=UTC request really is UTC.

Spot check against the forecast series, which is timezone-labelled by
Open-Meteo itself:
  Open-Meteo says timezone=GMT, utc_offset_seconds=0
  so both sides of the join are stamped in UTC and need no shifting.

Third check - the two spellings of UTC. The session 14 prompt describes
the existing request approach as tz=Etc/UTC; every request this project
has actually made uses tz=UTC. The same three days were pulled the
prompt's way, and compared with the first three days of the tz=UTC
sample - same fields, same station, same window, so the two responses
can be compared byte for byte.
  tz=UTC file     : iem_asos_DSM_2026-07-01_2026-07-22_routine.csv
                    first 73 lines (1 header + 72 rows), 4,146 bytes
  tz=Etc/UTC file : iem_asos_DSM_2026-07-01_2026-07-04_routine-etc-utc.csv
                    73 lines, 4,146 bytes
  byte-for-byte identical : YES
  So the two spellings are the same request. The project's tz=UTC needs
  no change; the prompt's wording and the code agree in substance.

PART C - plain first read
==========================================================================
A summary of what the checks above actually printed. Nothing here is a
decision; the owner decides what happens next.

1. Position. IEM's own record puts DSM at lat 41.534, lon -93.6531,
   elevation 294.0 m, timezone America/Chicago. That is what every
   forecast request in this session used - nothing was typed from a map.

2. Forecast source. The Previous Runs API carries DSM. Its grid point is
   lat 41.52945, lon -93.63281, elevation 285.0 m -
   1.76 km from the airport, -9.0 m in height. That is CLOSER than
   either European airport's grid point (4.33 km at EGLC, 3.44 km at LFPG)
   and the first height mismatch worth naming, though 9 m is small.
   Recent sample: 504 hourly rows, 0 missing.

3. Archive depth. 1-7 March 2021 comes back HTTP 200 with all 168 values
   null, and the first hour carrying a real value is 2021-03-24T00:00 UTC -
   the same hour as EGLC (F1) and LFPG (F20), to the hour. So the D13
   split dates need no moving for DSM either.

4. Target hour. America/Chicago's standard offset is UTC-6, so local
   standard noon is 18:00 UTC year-round, which is what D33 says.
   At 18:00 UTC the local clock reads 12:00 CST in winter and 13:00 CDT
   in summer - midday to early afternoon, matching how 12:00 UTC sat in
   Europe. 12:00 UTC would have been 06:00/07:00 local, at dawn.

5. Truth source. IEM carries DSM in IA_ASOS with a clean record. Both
   samples, five years apart, are complete apart from the first hour of
   each window, which is a request-boundary artefact rather than a gap.

6. Report timing. DSM reports at :54, every single report in both
   samples - 504 of 504 recently and 336 of 336 in 2021, with IEM's own
   METAR_RESET_MINUTE attribute saying 54 as well. That is 6 minutes
   before the hour, inside D14's 15-minute tolerance, so D14 applies as
   written at the 18:00 UTC target: the 17:54 report is the observation
   for 18:00. Not one report in either sample falls outside the
   tolerance, so on this evidence DSM loses no day to off-hour
   reporting - unlike LFPG, which loses three across five years (F25).

7. Units and timezone need no new handling. tmpc is degrees Celsius at
   DSM, agreeing with the Fahrenheit field to 0.005 degC across 72 rows,
   and the tz=UTC request really is UTC: pulled again in local time, the
   same temperatures line up exactly 5 hours later, which is the July
   UTC-5 daylight-saving offset. tz=UTC and tz=Etc/UTC return byte-for-
   byte the same rows.

8. Gap counts, nothing filled (SPEC 2.2). Recent sample: 504 hours
   expected, 503 covered, 1 missing (the boundary hour). Early sample:
   336 expected, 335 covered, 1 missing (the same boundary artefact).
   No report in either sample carries a missing temperature.

9. Plain verdict: YES - on this evidence DSM is usable for the recipe
   the same way EGLC and CDG were. Every verify-on-contact check passed,
   and the only thing that had to change is the target hour, which was
   changed on principle before any DSM data was seen (D33). Three-week
   samples cannot prove what the other five years look like; the full
   pull and its gap map settle that, exactly as session 10 did for CDG.
