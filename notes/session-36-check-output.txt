Task 4 -- grid->point interpolation + lead-time convention
-----------------------------------------------------------------------------

Lead-time convention, derived from SPEC 3.2's own description of how
Open-Meteo builds previous_day1 (hours 24-29 of each 6-hourly run, stitched)
and confirmed empirically below: for a target valid hour HH:00 UTC on day D,
use the run made at cycle floor(HH/6)*6 UTC on day D-1, forecast hour
24 + (HH mod 6).

  station  target hour  cycle  lead(fXXX)
  EGLC     12:00 UTC    12z    f024   (exact 24h -- on a cycle boundary)
  LFPG     12:00 UTC    12z    f024   (exact 24h -- on a cycle boundary)
  DSM      18:00 UTC    18z    f024   (exact 24h -- on a cycle boundary)
  YSDU     02:00 UTC    00z    f026   (26h -- 2h past the 00z boundary)
  RNO      20:00 UTC    18z    f026   (26h -- 2h past the 18z boundary)

Interpolation: bilinear across the 4 grid points ecCodes' own
codes_grib_find_nearest(npoints=4) returns for each airport's established
Open-Meteo grid point (SPEC 3.4 "grid latitude"/"grid longitude" columns --
the exact point the existing, trusted Open-Meteo temperature series already
answers for, not the raw airport position). Example (EGLC, 2025-06-11 12z
run, f024, valid 2025-06-12 12:00 UTC):

$ python3 -c "... codes_grib_find_nearest(gid, 51.487137, 0.0, npoints=4) ..."
51.25 0.25 294.821435625 dist=31.6 km
51.25 0.00 294.821435625 dist=26.4 km
51.50 0.25 296.721435625 dist=17.4 km
51.50 0.00 296.921435625 dist=1.4 km
-> bilinear (target lon exactly on the 0.0 grid line, so this collapses to a
   pure latitude interpolation) gives 23.66 degC; Open-Meteo's own value at
   the same valid hour is 23.9 degC -- a 0.24 degC difference, by hand before
   the full script existed, first evidence the approach works.

One real bug found and fixed by this check: the GRIB grid's longitudes come
back from ecCodes in 0-360 convention even when the query point is passed in
the codebase's normal -180..180 form (`codes_grib_find_nearest` itself
handles the negative input fine internally, but the neighbour lon0/lon1
returned are 0-360) -- the first version of the bilinear weight arithmetic
used the raw -180..180 query longitude against those 0-360 neighbour
longitudes, giving nonsense weights (dlon in the thousands) and multi-
hundred-degree "temperatures" at DSM and RNO (the two airports with negative
longitudes). Fixed by normalising the query longitude to 0-360 before
computing dlon (scripts/session36_validate.py). EGLC/LFPG/YSDU (all
non-negative longitudes) were unaffected and passed on the first run,
confirming the bug was specifically the sign/convention handling, not the
bilinear formula or grid read itself.

The four raw-GRIB grid points bracketing Reno's own established grid point
carry MODEL terrain elevations of 1591-1914 m -- 246-570 m HIGHER than
Reno's actual/grid elevation (1344-1345 m, SPEC 3.4). At a standard
environmental lapse rate (~0.65 degC/100 m), that spread alone predicts
roughly 1.6-3.7 degC of cooling in a plain grid-average temperature relative
to a point corrected down to the true 1345 m elevation -- squarely
consistent with the measured -2.04 degC mean bias. Open-Meteo's own
published value is evidently already elevation-corrected for its target
point (a known downscaling step, expected especially in complex terrain);
this session's bilinear-only pipeline is not, and RNO -- alone among the
five airports -- sits in terrain steep enough (the same Sierra Nevada front
SPEC 3.4 and DECISIONS D42/F66 already name as Reno's real difficulty) for
that gap to show up as a multi-degree, one-sided bias rather than noise.
The other four airports' own grid-to-airport elevation mismatches are all
under 10 m (SPEC 3.4), so any lapse-rate correction there would be
sub-tenth-of-a-degree -- consistent with their small, mixed-sign residuals
being ordinary rounding/interpolation noise rather than a masked version of
the same effect.

RNO verdict: FAIL, cause named -- not wrong grid points (confirmed: the same
established SPEC 3.4 point was used), not wrong cycle/lead (valid_ok=True
every row; the SAME modulo-offset lead-time formula reproduces YSDU cleanly),
not a unit/label error (shortName '2t', K, matches EGLC/LFPG/DSM/YSDU
exactly) -- but a missing elevation/lapse-rate correction step this session's
plain bilinear interpolation does not perform and Open-Meteo's own pipeline
evidently does, made visible specifically at Reno because of real local
terrain relief the raw 0.25 deg grid does not resolve.

OVERALL VERDICT: the GRIB->point pipeline is PROVEN for 4 of 5 airports
(EGLC, LFPG, DSM, YSDU) exactly as pulled (byte-range TMP:2m, the derived
cycle/lead convention, plain bilinear interpolation) -- sub-degree, unbiased
differences against the trusted Open-Meteo answer key, at both the archive
floor and a recent date. It is NOT yet proven at RNO: the interpolation and
lead-time logic are not implicated (both check out), but a same-terrain
elevation-correction step is evidently needed before RNO's own richer-feature
work could trust a raw-GRIB pull the way it trusts Open-Meteo's already-
corrected series. This is a fix to make before RNO's data enters step 2's
bulk pull, not a reason to distrust the pipeline at the other four airports.
